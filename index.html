문서화를 시작한 이유

AI가 없던 학부 시절, 직접 공부한 내용을 정리하거나 경험한 오류에 대해 기록하기 위해 시작했습니다.

직접 쓴 글들은 저뿐만 아니라, 같은 고민을 하던 친구와 후배, 그리고 블로그를 찾아온 독자들의 시간을 아껴주었습니다.


개발자에게 문서화란 단순한 기록이 아닌, 경험을 팀의 자산으로 만드는 행위입니다.

그 생각을 바탕으로 4년간 트러블슈팅 기록, 개념 정리, 구현 회고, 개발 외적 요소들에 대해 꾸준히 써왔고, 어느새 270편이 넘었습니다.


지금까지도 한 편의 글이 저를 포함한 누군가의 시간을 아껴줄 수 있다는 마음으로, 개발의 흔적을 기록해나가고 있습니다.

TECHNICAL CHALLENGES
01
MD 기반 문서화 문화 구축과 Claude Code 컨텍스트 활용
문제MSA 7개 서비스 분담 개발로 타 모듈 파악에 매번 시간 소요. Claude Code 세션 초기화 시 컨텍스트 재설명 비효율도 존재
해결별도 도구 도입 대신 Git repo 내 docs/ 폴더에 서비스별 설계 결정 / API 명세 / 장애 대응 흐름 MD 정리 (13개 카테고리 구조화). 작성한 MD를 Claude Code 컨텍스트로 활용해 타 모듈도 빠르게 파악
팀 내 반복 질문 제거 · 기록이 쌓일수록 Claude Code 컨텍스트 품질 향상 → 팀 전체 개발 생산성 증대
02
서버 리소스 이슈 #1 — Elasticsearch 도입 결정 과정 (p95 31% 개선)
문제JPA LIKE %keyword% 앞 와일드카드로 Full Table Scan — 유명 셀러 클래스 오픈 시 단시간 트래픽 집중, 데이터 규모 증가 시 선형 비용 증가
해결t3.large 리소스 제약으로 ES 도입 전 PostgreSQL pg_trgm GIN 인덱스로 먼저 검증 (p95 12% 개선, 극한 부하 실패 14건). 수치로 한계 확인 후 ES 도입, nori 형태소 분석기로 한국어 전문 검색 지원
p95 1,879ms → 1,294ms (Full Scan 대비 31% 개선) · 실패율 0% · 데이터 100배 증가 시 ES +85% vs DB +153% (ES 확장 안정성 확인)
아키텍처
03
서버 리소스 이슈 #2 — 단일 ES 노드 SPOF 제거, Resilience4j 서킷 브레이커 + Fallback
문제검색 로직 전체를 ES에 위임한 구조 → ES 장애 시 검색 API 전체 오류(SPOF). t3.large 리소스 제약으로 ES 노드 추가 불가
해결Resilience4j Circuit Breaker 적용, ES 장애 감지 즉시 PostgreSQL fallback 전환. ES 컨테이너 강제 종료 카오스 테스트로 CB 상태 전이(OPEN → HALF_OPEN → CLOSED) 검증
ES 장애 중 검색 API 실패율 0% (fallback 응답 지속) · ES 복구 후 CB 자동 전환 확인
아키텍처
04
검색 기능 장애 대응 — Race Condition으로 인한 ES Dynamic Mapping 문제
문제매일 EC2 재시작 시 Kafka consumer가 인덱스 초기화보다 먼저 실행되어 nori 빠진 매핑이 디스크에 영속화 — 재시작해도 복원 불가, 한국어 형태소 분석 장애로 이어짐
해결@PostConstruct로 전환해 bean 생성 시점에 인덱스 초기화를 Kafka consumer 등록 전 반드시 선행 보장. @Document, @Setting, @Field로 명시적 매핑 정의 → Dynamic Mapping 원천 차단
Race Condition 근본 원인 제거 · 명시적 매핑으로 nori 분석기 누락 재발 방지
아키텍처
05
Admin 모듈 다중 도메인 DataSource 통합과 커넥션 풀 최적화
문제Admin 서비스는 5개 도메인 테이블에 동시 접근 필요. 초기 도메인별 DataSource 4개 분리 구성으로 HikariCP 기본값(10개)씩 점유 → 이론상 최대 40개 커넥션 점유
해결AdminDataSourceConfig 하나로 통합 (5개 도메인 단일 풀 공유), TransactionManager도 1개로 정리. Admin 트래픽 특성(저트래픽·조회 위주) 고려해 maximum-pool-size: 2 / minimum-idle: 1로 튜닝
최대 점유 커넥션 40개 → 2개로 축소 · 단일 DB 커넥션 리소스 효율화

TECHNICAL CHALLENGES
01
동시 출석 등록 Race Condition — DB Unique 제약으로 중복률 0% 달성
문제여러 관리자가 동시에 동일 인원 출석 등록 시 중복 저장 — 애플리케이션 단 검증만으로는 Race Condition 차단 불가
해결@Column(unique=true)로 DB 레벨 INSERT 직렬화, DataIntegrityViolationException → IllegalStateException 변환. 동명이인은 차단 대신 분기 안내로 누락 방지
데이터 중복률 0% · 무결성 100%
아키텍처
02
전체 인원 일괄 갱신 1+N 쿼리 — JPA 벌크 연산으로 N회 → 1회 단축
문제JPA 기본 메서드는 SELECT 1회 + UPDATE/DELETE N회로 동작 — 전체 인원 일괄 갱신 시 1+N 쿼리 발생
해결@Modifying(flushAutomatically=true) + 커스텀 JPQL로 영속성 컨텍스트 우회, DB에 단일 쿼리 직접 전송
쿼리 실행 횟수 N회 → 1회
아키텍처
03
소그룹 편성 자동화 — 다중 필터링 기반 랜덤 알고리즘 구현
문제매주 수동 편성으로 관리자 리소스 소모 및 인적 편향 개입 가능
해결isExcluded·isHard 기반 2단계 필터링 후 특수 인원 균등 선배치 → 일반 인원 라운드로빈 + Collections.shuffle(). 파이프라인 구조로 신규 조건 추가 시 확장 용이
수동 편성 → 클릭 1회 자동화 · 편성 공평성 기술적 보장 · O(N + T) ≈ O(N) 의 시간복잡도(선형 시간)로 동작
아키텍처

단순한 코드 생성 도구를 넘어, AI를 다음과 같이 활용하고 있습니다.

01
CLAUDE.md로 컨벤션 내재화
  • 팀 아키텍처 제약, 커밋 컨벤션, 행동 지침을 CLAUDE.md로 코드화
  • 7개 마이크로서비스에 걸쳐 일관된 패턴 유지
  • "Think Before Coding / Simplicity First / Surgical Changes" 원칙 적용
02
Karpathy Skills 적용
  • Andrej Karpathy가 지적한 LLM 코딩 함정(과가정·과복잡화·코드 무단 변경)을 CLAUDE.md 가이드라인으로 선제 차단
  • Pro 요금제 한계를 고려해 토큰 효율을 높이는 프롬프팅 구조 설계
Karpathy Skills 란?

OpenAI 공동 창립자이자 Tesla AI 개발 부분 총괄이사인 Andrej Karpathy가 관찰한 LLM 코딩 함정 4가지를 CLAUDE.md로 코드화한 오픈소스. GitHub ↗

  1. 과가정 차단 — 불확실하면 가정하지 않고 먼저 질문
  2. 과복잡화 차단 — 요청하지 않은 기능/추상화 추가 금지
  3. 코드 무단 변경 차단 — 요청 범위 밖 코드 수정 금지
  4. 목표 기반 실행 — "무엇을 하라" 대신 "무엇이 되어야 한다"로 지시
03
docs/ MD로 컨텍스트 관리
  • 잡아클래스 프로젝트에서 13개 카테고리 MD 문서화
  • Claude Code 세션 초기화 시 docs/를 컨텍스트로 주입해 재설명 비용 제거
  • 팀원이 담당한 모듈도 MD 기반으로 즉시 파악
04
git 히스토리 기반 교차 검증
  • AI 산출물을 그대로 수용하지 않고 git log / git diff로 직접 검증
  • 실제 사례: Admin 모듈 커넥션 풀 튜닝 수치(40→2)를 git 히스토리로 추적해 정확한 수치 도출
05
Claude App → Claude Code 2-Stage 워크플로우
  • 설계·방향·프롬프트 설계는 Claude App에서 (대화 기반 사고)
  • 확정된 프롬프트를 Claude Code에 전달해 실제 구현 실행
  • "무엇을 만들지"와 "어떻게 만들지"를 분리해 AI 산출물의 품질 통제
06
위임 경계 명확화
  • AI에 위임 — 보일러플레이트 생성, JPA 코드 작성, git diff 분석, 컨벤션 적용
  • 직접 판단 — 트랜잭션 경계, 락 전략, Database / DataSource 설계, 아키텍처 결정
